# 性能の測定記録

数字は**測定条件とセットでなければ意味を持ちません**。ここでは、何を・どこで・どう測ったかを
明示します。**1台の環境での測定であり、他の環境での性能を保証するものではありません。**

測定日: 2026年9月 / ツール版: v3.1.0（一部は開発途中の版。各項目に明記）

---

## 1. 測定環境

| | |
|---|---|
| iPhone | iPhone 11 Pro Max / iOS 26.6.1 |
| 接続 | Apple純正USBケーブル / PC本体のUSBポート（ハブ非経由） |
| PC (A) | Windows 10 |
| PC (B) | Windows 11 / AMD Ryzen AI 9 365 / RAM 32GB |
| 保存先 | NTFS・5.45TB（キャッシュと同一ドライブ） |
| 対象 | 写真アプリ上 80,389項目 / 実ファイル 84,173個 / 166.8GB |

> **iPhone 11 Pro Max の Lightning端子は USB 2.0 です。** PCの性能や保存先ドライブの速度を
> 上げても、この上限を超えることはできません。

## 2. USB転送の実測（実機）

### 2-1. 大きい単一ファイル（写真データベース 約7GB）

| 版 | サイズ | 所要 | 実効速度 |
|---|---:|---:|---:|
| 開発中（v2.x） | 7,134 MB | 270秒 | **26.4 MB/s** |
| v3.x | 7,138 MB | 203秒 | **35.2 MB/s** |

同じ端末・同じケーブルでも実行ごとに幅があります（26〜35 MB/s）。
USB 2.0の理論値は60 MB/sですが、実効はこの程度です。

### 2-2. 小さいファイルが大量（写真本体）

| 内容 | 量 | 所要 | 実効速度 | 1枚あたり |
|---|---:|---:|---:|---:|
| 初回・前半 17,500ファイル | 29.0 GB | 41分 | **12.1 MB/s** | 1.70 MB |
| 初回・後半 66,567ファイル | 137.7 GB | 264分 | **8.9 MB/s** | 2.12 MB |

**同じ経路なのに、大きい1ファイルの 1/3 以下の速度**しか出ていません。

### 2-3. 差の分析（推定を含む）

2-1の速度を上限と仮定して、2-2の所要時間から「転送そのもの」を引くと、残りが
1ファイルごとの手続き（開く・読む・閉じる）のコストになります。

| 上限の仮定 | 前半の往復コスト | 後半の往復コスト |
|---|---:|---:|
| 35.2 MB/s とした場合 | 92 ms/件 | 178 ms/件 |
| 26.4 MB/s とした場合 | 76 ms/件 | 158 ms/件 |

**1件あたり概ね 80〜180 ms**。84,000ファイルなら、これだけで **2〜4時間**に相当します。
写真1枚が平均2MB程度しかないため、転送時間より手続きの時間のほうが長くなります。

> **これは推定です。** 上限速度の仮定によって結果が変わりますし、
> 内訳（AFCの往復・ローカル書き込み・ウイルス対策の介在）を個別に計測したものではありません。
> 「小さいファイルが大量にあると、1件ごとの固定コストが支配的になる」という傾向を示す数字として
> ご覧ください。

### 2-4. 初回バックアップの実測

| 条件 | 所要 |
|---|---:|
| 84,000ファイル・約167GB を新規取得 | **4時間24分** |
| 同じ内容を2回目（差分のみ10,326件） | **11分** |

## 3. ローカル処理の測定（USB転送は含まない）

**ここからはUSB転送と無関係です。** Pythonのバイト列連結が遅い問題を切り分けるため、
Linuxコンテナ上で、同じデータ量を3通りの方法で処理した時間を測りました。

測定環境: Linux 6.18 / Python 3.12.3 / 4MBずつ処理

| データ量 | ① メモリ上で連結<br>`data += chunk` | ② ファイルへ逐次書込<br>（OSキャッシュ含む） | ③ ファイルへ逐次書込<br>＋fsync |
|---:|---:|---:|---:|
| 100 MB | 1.49秒 | 0.027秒 | 0.41秒 |
| 200 MB | 3.93秒 | 0.062秒 | 0.21秒 |
| 400 MB | 16.43秒 | 0.084秒 | 0.40秒 |
| 800 MB | 66.28秒 | 0.225秒 | 0.96秒 |

**②の数字だけを引用すべきではありません。** ②はOSの書き込みキャッシュに載った時点の時間で、
ディスクへの反映を待っていません（200MBを0.062秒＝3.2GB/sは、物理ディスクの速度ではありません）。
ディスクへの反映まで含めた③と比べるのが公平です。

読み取れること:

- **①は超線形に悪化します**。データ量8倍（100→800MB）で時間は約44倍。
  バイト列は変更できないため、`+=` のたびに全体がコピーされることが原因です
- ②③は概ねデータ量に比例します
- 400MBの時点で **①は③の約41倍**

### 3-1. 実際の効果（実機）

上記は模擬実験ですが、修正の効果は実機でも確認できました。

| | 所要 |
|---|---:|
| 修正前（`data += chunk` 方式）の7GB取得 | 40分経過時点で未完了。外挿で**約1.6時間** |
| 修正後（逐次書き込み）の7GB取得 | **203秒** |

外挿値は実測ではないため「約」としています。確実なのは、**修正後は203秒で完了する**ことです。

## 4. 再スキャンの往復回数（模擬環境での測定）

2回目以降の実行で、取得済みファイルの確認をiPhoneに問い合わせるかどうかの差です。
**擬似的なAFC実装に対する往復回数のカウント**であり、実機の所要時間ではありません。

| | iPhoneへの問い合わせ回数 |
|---|---:|
| 毎回サイズを確認（既定・安全側） | ファイル数と同数（84,000件なら84,084回） |
| 「2回目以降を高速化する」をON | フォルダ数のみ（84回） |

1往復を40msと仮定すると約56分の差になりますが、**この40msという仮定自体が推定**です。
実機での短縮効果は測定していません。

なお高速化をONにすると、端末側で**同名のまま中身が差し替わった写真を検出できません**。
このため既定はオフです。

## 5. 容量の測定

| | 値 |
|---|---:|
| 写真の実体（キャッシュ） | 166.8 GB |
| エクスプローラーのフォルダ表示 | **540 GB** |
| ファイル数（リンクを含む） | 255,205 |

表示が約3.2倍になるのは、**エクスプローラーがハードリンクを1件ずつ数える**ためです。
1枚の写真が「キャッシュ・アルバム・種類別フォルダ」に現れると3回加算されます。
ディスクの実消費は166.8GBのままで、`fsutil hardlink list` で同一実体であることを確認しています。

詳細と確認手順は `verification.md` を参照してください。

## 6. 速度を改善したい場合

測定の結果、効果が期待できる順です（**いずれも本環境での経験に基づく推奨で、
効果を保証するものではありません**）。

1. **保存先フォルダをウイルス対策の除外に追加する**
   数万個のファイルを1つずつ検査されるのを避けられます。書き込みエラーの予防にもなります
2. **保存先ドライブの「内容にインデックスを付ける」をオフにする**
3. **USBハブを使わず、PC本体のポートに直接挿す**
4. **「アルバム情報を取り直す」は必要な時だけチェックする**
   毎回だと約7GBの再取得で3〜5分増えます
5. バックアップ中はiPhoneを操作しない

**逆に、効果が無いこと**: PCのCPU・メモリの強化、保存先をより高速なSSDにすること。
上限はiPhone側のUSB 2.0で決まります。

## 7. この記録の限界

- **1台のiPhone・2台のPCでの測定**です。他の機種・環境では異なります
- 内訳（AFCの往復／ローカル書き込み／ウイルス対策）を個別に計測していません
- 3節のローカル測定はLinuxコンテナ上であり、Windows上の数字ではありません
- 4節は模擬環境での往復回数であり、実機の時間ではありません
- 同じ測定でも実行ごとに幅があります（2-1で26〜35 MB/s）
